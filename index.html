Bloque 1 · Diaz Vazquez Regina Valeria

Clasificación de dispositivos: tres ejes, no una lista

Un móvil se define por la intersección de su potencia física, su geometría y la forma en que recibe órdenes. Toca cada eje del diagrama.

Hardware: el techo real de la experiencia

La potencia de CPU/GPU define cuánto JavaScript puede ejecutarse antes de bloquear el hilo principal; la batería y la temperatura imponen un presupuesto que ninguna optimización de CSS puede ignorar.

CPU / GPURAMBateríaGPSGiroscopioAcelerómetroCámaraLuz ambiental

Consecuencia web: sensores accesibles solo bajo HTTPS y con permiso explícito (Geolocation, DeviceMotion, getUserMedia).

Factor de forma: ergonomía antes que píxeles

Tamaño físico, peso y geometría del panel. La zona de alcance del pulgar determina dónde colocar acciones primarias; el formato del panel cambia el layout utilizable.

  • Plano: barra superior y navegación inferior alcanzables con una mano.
  • Circular: relojes; información en una sola capa, interacción de 2–3 s.
  • Articulado: plegables; el viewport cambia en caliente y el layout debe reflow sin perder estado.

Interfaz: cómo entra la intención

La capacidad de entrada define el tamaño de los objetivos táctiles, la necesidad de alternativas al :hover y el diseño de la retroalimentación.

Táctil · 44×44 pxStylus · precisión finaVozGestosEye tracking · dwell

Regla práctica: si la acción crítica depende de hover o de un objetivo menor a 44 px, no es usable en móvil.

Tres ejes · un detalle a la vez.

Bloque 1 · Del dispositivo al CSS

Lo que el hardware le exige a tu hoja de estilos

Cuatro decisiones de CSS y HTML separan una interfaz que se adapta de una que se recorta. Abre cada viñeta o usa el inspector.

El viewport es el área visible en píxeles lógicos, no la resolución física. La barra de URL móvil aparece y desaparece: 100vh se calcula con el viewport más grande y provoca recortes. Usa 100dvh para altura real y 100svh para el mínimo estable. Diseña Mobile-First con Grid y Flexbox antes de añadir @media.
El DPR relaciona píxeles físicos con lógicos (2×, 3×). Un PNG de 300 px puede verse borroso en 900 px físicos. Sirve SVG para iconos y srcset + sizes para fotos; reserva el 3× a imágenes críticas y deja que el navegador elija.
Conviven 20:9, 4:3, 1:1 y pantallas plegables. Evita alturas fijas y usa aspect-ratio, min-height con dvh y contenedores que puedan crecer. Prueba en horizontal: no bloquees la orientación sin una razón funcional.
Objetivo mínimo de 44×44 px con 8 px de separación, sin depender de :hover: en táctil no existe. Diseña estados :active y :focus-visible, soporta swipe y zoom, y evita user-scalable=no.

Inspector de viewport

100vh · barras superpuestas contenido recortado
Compara 44×44 px con 24×24 px: el segundo incumple el mínimo táctil.

En móvil, dvh ajusta la altura cuando aparecen las barras del navegador; vh mantiene la medida grande y esconde la última fila.

Bloque 2 · Cruz Contreras Jonathan Ivan

Ecosistemas: la cuota define a quién optimizas

La distribución mundial no es una curiosidad estadística: decide qué motor, qué APIs y qué modelo de monetización encuentras en producción.

Android · 72.4%

volumen global y México

Código abierto (Linux + AOSP) sobre hardware de cientos de marcas y gamas. Esa fragmentación es la fortaleza del alcance y la causa de la variabilidad de rendimiento.

  • Arquitectura: kernel Linux, HAL, ART y apps; el fabricante añade capas.
  • Distribución: Play Store + tiendas alternativas + APK.
  • Monetización: suscripciones, anuncios y compras; ticket medio más bajo que iOS.

iOS · 27.5%

retención y monetización

Ecosistema cerrado y exclusivo de Apple: control total de hardware y software, con soporte prolongado y una base que actualiza rápido.

  • Arquitectura: SoC propio, WebKit obligatorio para todo navegador.
  • Distribución: App Store como única vía general.
  • Monetización: mayor ARPU y conversión; usuarios concentrados en gamas altas.

SO ligeros · 0.1%

512 MB–2 GB RAM

KaiOS y Android Go priorizan arranque rápido y bajo consumo. Ejecutan apps ligeras basadas en HTML5, CSS y JavaScript.

  • Contexto: mercados emergentes, dispositivos de entrada y feature phones.
  • Restricción: poca memoria, CPU lenta y almacenamiento mínimo.
  • Oportunidad: una PWA bien medida ofrece más valor que una app nativa pesada.

Bloque 2 · Motores de renderizado

Dos motores, dos ciclos de vida

El motor decide qué APIs puedes usar hoy y cuándo llegan las correcciones. Compara por criterio, no por preferencia.

Blink · ~72% móvil WebKit · ~26% móvil Resto · motores propios y WebViews antiguos
B

Blink · Chromium

Chrome, Edge, Opera, Samsung Internet, WebView

Commit upstream→Canary / Beta→Play Store→WebView

Actualizaciones independientes del sistema operativo. Una corrección de seguridad puede llegar en semanas, no en años; también puedes adoptar APIs nuevas antes.

W

WebKit · Safari

Safari y todo navegador dentro de iOS

Commit upstream→Beta→Actualización del SO

El motor viaja con la versión de iOS. Sin actualización del sistema no hay motor nuevo: usuarios en versiones antiguas condicionan el browser support matrix.

Blink adopta antes

  • PWA instalables, Push y Background Sync maduros.
  • WebGPU disponible de forma amplia; Wasm con soporte completo.
  • Web Bluetooth, Web NFC y File System Access en Chromium.

WebKit prioriza privacidad y batería

  • Push web limitado y sin Background Sync clásico.
  • Web Bluetooth y Web NFC no disponibles en Safari.
  • WebGPU llegó más tarde y con cobertura parcial.

Un solo motor para todos los navegadores

En iOS, Chrome, Firefox y Edge usan WebKit como motor de renderizado. No puedes desplegar una capacidad que WebKit no implemente, aunque el usuario tenga otro navegador instalado.

Consecuencia práctica: define la experiencia base con APIs estables y mejora progresivamente (progressive enhancement); nunca asumas paridad entre plataformas.

Bloque 3 · Enriquez de la Cruz Emmanuel

Responsivo vs. adaptativo: flujo continuo o saltos

Ambos usan breakpoints; la diferencia es qué ocurre entre ellos. Cambia el ancho y el modo para verlo.

340 px · 1 columna
RWD · cuadrícula fluida ancho 340 px

Las columnas se recalculan con minmax() y auto-fit: el layout respira en cualquier punto intermedio.

Diseño responsivo (RWD)

Cuadrículas fluidas, unidades relativas y @media para ajustes finos. Un solo documento se adapta de forma continua; es el enfoque que sostiene el Mobile-First.

Diseño adaptativo (AWD)

Layouts estáticos servidos para breakpoints predefinidos. Predecible y fácil de probar, pero entre dos breakpoints el contenido puede quedar desproporcionado o con espacio muerto.

Mobile-First

Diseñar primero para la pantalla más restrictiva obliga a priorizar jerarquía, contenido y peso. Después se escala: añadir columnas es más barato que recortarlas.

Bloque 3 · Progressive Web Apps

Una app web que se comporta como nativa

Instalable, offline y notificable sin tienda. Toca cada nodo de la arquitectura para ver el contrato técnico.

App UI · la capa visible

Interfaz construida con estándares web. Debe funcionar sin conexión para las rutas críticas y mostrar estados honestos: sin conexión, datos en caché o pendientes de sincronizar.

HTML5CSS3JSresponsive

Service Worker · proxy en segundo plano

Script independiente del DOM que intercepta fetch, decide caché o red, y recibe eventos como push y sync. Solo funciona bajo HTTPS y no puede acceder al DOM directamente.

fetchcache-firstsyncpush

Web App Manifest · identidad instalable

JSON con nombre, iconos, colores y display. Permite instalar en la pantalla de inicio y abrir en modo standalone, sin barra del navegador.

nameiconstheme_colorstandalone

Cache API + IndexedDB · memoria persistente

Cache almacena respuestas HTTP (HTML, CSS, fuentes, imágenes); IndexedDB guarda datos estructurados y colas de operaciones. Las cuotas son del navegador y pueden ser desalojadas.

Cache APIIndexedDBBackground Sync

Ventaja medible: primera carga controlada por red; siguientes, controladas por caché.

Bloque 3 · Híbridas vs. nativas

Un código base contra el acceso total al hardware

La decisión no es ideológica: es un intercambio entre costo, tiempo y control del dispositivo. Selecciona un criterio.

Capas de una app híbrida

El puente es potente y delicado: cada mensaje cruza una frontera de seguridad y de rendimiento.

CriterioNativoHíbrido / WebView
RendimientoMáximo · GPU directaDepende del WebView
CostoDos desarrollosUn código base
Time-to-MarketMás lentoRápido · hot reload

Dónde la web móvil ya reemplaza a la app

Cuatro sectores donde el navegador gana por fricción de instalación, acceso a hardware o consumo de datos.

Comercio electrónico y Fintech

  • Conversión rápida: cada paso extra de instalación pierde usuarios; la web abre directo desde el anuncio.
  • Pagos en un clic: Payment Request API reutiliza tarjeta y dirección del navegador.
  • Biometría: WebAuthn permite autenticación con huella o rostro sin contraseña.
  • Catálogos offline: Cache API e IndexedDB para consultar sin señal.
Payment RequestWebAuthnIndexedDB

Ejemplos: AliExpress, Amazon móvil, Mercado Pago Web.

Movilidad y Mapas

  • Rutas en tiempo real: el mapa se actualiza sin descargar una app pesada.
  • Bajo consumo de datos: tiles vectoriales y caché reducen el tráfico frente a un cliente nativo.
  • Contexto inmediato: enlace compartido que abre la ruta exacta en el navegador.
  • Geolocalización: GPS + Wi-Fi + celdas con permiso puntual, no permanente.
GeolocationCache APISVG

Ejemplos: Uber Lite m.uber.com, Google Maps Web.

Salud y Fitness

  • Telemedicina en navegador: videollamada con getUserMedia sin instalar software.
  • Conexión con wearables: Web Bluetooth para básculas y monitores cardíacos compatibles.
  • Privacidad primero: el permiso de cámara y micrófono se concede por sesión y por origen.
  • Continuidad: historial accesible desde cualquier dispositivo con sesión iniciada.
getUserMediaWeb BluetoothPush

Consumo Multimedia

  • Streaming adaptativo: HLS/DASH ajusta la calidad según red y batería.

  • Controles del sistema: Media Session API publica título y carátula en la pantalla de bloqueo.

Bloque 4 · Hardware desde el navegador

Cinco APIs, un requisito: HTTPS y permiso

El navegador es un intermediario desconfiado. Cada capacidad del dispositivo se concede por origen, por sesión y con consentimiento explícito.

Geolocalización

Geolocation API

Combina GPS, Wi-Fi y redes celulares. Devuelve latitud, longitud, precisión, velocidad y rumbo. Requiere HTTPS y permiso; en segundo plano el navegador puede degradar la precisión.

navigator.geolocation.getCurrentPosition(ok, err, { enableHighAccuracy: true })

Cámara y micrófono

MediaDevices

Videollamadas, escaneo de QR o tarjetas y base para Realidad Aumentada con WebXR. El usuario ve qué dispositivo se solicita y puede revocarlo.

navigator.mediaDevices.getUserMedia({ video: { facingMode: 'environment' } })

Sensores de movimiento

DeviceMotion

Acelerómetro y giroscopio: inclinación, rotación, sacudidas y podómetro aproximado. Sin permiso en iOS y subject to sensor throttling.

DeviceOrientationEvent.requestPermission() · 'devicemotion'

Notificaciones push

Push + Notifications

El Service Worker recibe el evento con la app cerrada. Requiere suscripción PushManager, claves VAPID y permiso explícito; nunca debe pedirse en la primera visita.

registration.pushManager.subscribe({ userVisibleOnly: true })

Bluetooth y NFC

Web Bluetooth / NFC

BLE para básculas y monitores cardíacos; NFC para etiquetas de proximidad y credenciales. Soporte desigual: no disponible en Safari iOS.

navigator.bluetooth.requestDevice({ acceptAllDevices: true })

Regla: pide el permiso en el momento en que el usuario entiende para qué sirve (Just-in-Time), no al cargar.

Bloque 5 · Superficie de ataque híbrida

El puente nativo es una frontera, no un atajo

Sin blindaje

Capacitor, Cordova e In-App Browsers ejecutan contenido web dentro de un contenedor con acceso a APIs nativas. Todo lo que entra al WebView puede intentar cruzar el puente.

Content-Security-Policy con default-src 'self', sin unsafe-inline ni unsafe-eval. Bloquea scripts inyectados y orígenes no declarados antes de que se ejecuten.
Lista blanca de hosts permitidos dentro del WebView y en aperturas externas. Cualquier redirección fuera del dominio conocido se cancela y se registra, en lugar de abrirse.
Deshabilita el acceso a archivos locales y la carga de contenido mixto. Un file:// mal configurado permite leer recursos del dispositivo y saltarse el modelo de origen.
